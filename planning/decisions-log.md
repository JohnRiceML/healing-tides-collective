# Decisions Log

This is the project's **ADR log** (Architecture Decision Records) — the source of truth for *why* the system is the way it is. **Append-only:** to change a past decision, add a new entry that supersedes it (link back); don't edit history. Keep each entry to ~a page. See also the living-doc system in [AGENTS.md](../AGENTS.md) and [docs/SYSTEM.md](../docs/SYSTEM.md). Format:

```
## YYYY-MM-DD — Short title
**Decision:** What we picked.
**Why:** The reasoning.
**Alternatives considered:** What we passed on.
**Revisit when:** Trigger for re-evaluating.
```

## 2026-05-31 — "Sharded schema" reframed (research finding)
**Decision:** Do NOT replicate the SubredditSignals data pattern. Use a single dedicated Postgres per the entry above.
**Why:** Investigated the three repos John referenced. SubredditSignals is a single **MySQL** monolith where four products (Narrative Nooks `nn_*`, Subreddit Signals `ss_*`, GrowthMindset `gms_*`, CreatorReach `cr_*`) coexist via **table-name prefixes** — namespace isolation, not sharding. Mochi and Narrative Nooks have no standalone code repos (NN's models live inside SubredditSignals). There is no reusable sharding pattern to copy; the desired "isolated product DB + own services" pattern lives in counsel-post instead.
**Alternatives considered:** Prefix-namespacing HTC into a shared DB — rejected (data-boundary + isolation requirement).
**Revisit when:** N/A — recorded to prevent re-investigating.

## 2026-05-31 — Provisioning posture: Vercel-native, migrate-later
**Decision:** Provision the Phase 2 stack through the **Vercel Marketplace** where available (Neon, Clerk, Resend — auto-injected env vars + unified billing); wire Stripe directly. Favor Next.js primitives (Server Actions, route handlers, middleware) over bespoke infra. Treat the stack as a fast managed starting point we can migrate from later.
**Why:** The locked stack already *is* the Vercel/Next.js-recommended path, so going native costs nothing and removes setup toil. Starting managed maximizes velocity; portability is preserved — Neon is plain Postgres, Stripe/Resend are standard/swappable, and only Clerk carries real switching cost (bounded by the local `User`-mirror design + a thin `auth-clerk` surface). Full table in `docs/architecture/PHASE-2-SYSTEMS.md`.
**Alternatives considered:** Hand-provisioning each service outside the Marketplace (more toil, same result); adopting Vercel-proprietary primitives (Blob / Edge Config / Queues) up front — deferred until a real need to protect portability.
**Revisit when:** A Vercel-proprietary primitive becomes genuinely needed, or migration off Clerk is triggered.

## 2026-06-01 — Clerk widgets: render Clerk's native card, don't wrap/flatten it
**Decision:** On `/join` and `/sign-in`, let Clerk's `<SignUp>` / `<SignIn>` render its **own native, self-contained card**. Stop fighting the vendor widget. Verified headless on prod (desktop + mobile, both routes). Commit `9e5bd86`.

A fully custom Clerk flow (no `<SignUp>` component) — rejected (overkill; loses Clerk's maintained UX + security flows).

## 2026-06-01 — Public practitioner listing: one read layer, `www` canonical, publish via existing fields
**Decision:** Ship the public listing (`/practitioners` directory + `/practitioners/[slug]` SEO profile + `/sitemap.xml`) on three rules: (1) **one public read layer** — `lib/practitioners.ts` is the *only* place public surfaces read practitioner data, and it returns **PUBLISHED-only** via explicit field allow-lists (no `userId` / `email` / Stripe / internal fields ever reach the client). (2) **Publish is pure app code, no migration** — the `Practitioner.visibility` enum + `slug @unique` already existed, so `app/practitioner/publish-actions.ts` just flips `DRAFT→PUBLISHED` and mints a collision-safe slug. (3) **`www` is the single canonical origin** — `lib/site.ts` exports `SITE_URL = https://www.healingtides.co`, used by the root layout, the profile metadata/JSON-LD, and the sitemap.
**Why:** A public surface's top risk is data exposure; funneling every public read through one PUBLISHED-only module with allow-list `select`s makes that auditable in a single file (adversarial review confirmed no PII leak + no draft-by-slug bypass). Reusing the existing schema kept the whole feature **off** the shared/prod DB — no migration, and when seeding fake practitioner rows to verify was (correctly) blocked by the safety layer as shared-state pollution, verification used **local env-gated fixtures** instead. The canonical rule matters because the apex `healingtides.co` **307-redirects to `www`**, yet the root layout had been advertising the apex — splitting the very SEO signal the listing exists to earn; one `SITE_URL` constant ends the drift.
**Alternatives considered:** Per-page Prisma queries — rejected (the published-only rule would be duplicated and drift). A new `published` boolean + migration — rejected (the `visibility` enum already covers it). Apex as canonical — rejected (it's the redirecting host). Seeding test rows in Neon to verify — rejected/blocked (shared-DB pollution); used local fixtures.
**Revisit when:** Pagination is needed (the directory's `take: 200` cap), photo upload lands (add the Vercel Blob host to `next.config` image `remotePatterns`, upgrade `<img>`→`next/image`), or the admin / claim / email slice ships.
**Built by:** a 3-agent team (profile page / directory / editor control) on a lead-authored data + publish contract; verified via headless screenshots (desktop + mobile, with local fixtures) + an adversarial code review whose one BLOCKER (canonical host) and security should-fixes (website-scheme guard, dropped unused `socialLinks`) were addressed before ship.

## 2026-06-01 — Test suite: Vitest, extract-pure, mock-the-boundaries
**Decision:** Adopt **Vitest** (+ v8 coverage, `vite-tsconfig-paths` for the `@/*` alias) as the runner; tests live in `tests/`, run via `npm test` (now part of the quality gate). Strategy: (1) **extract pure logic** out of the `"use server"` files — which may only export async functions — into `lib/slug.ts`, `lib/url.ts`, `lib/completeness.ts`, so it's directly unit-testable; (2) **mock the boundaries** (`@/lib/db`, `@/lib/auth`, `next/cache` via `vi.mock`/`vi.hoisted`) to test the public read layer + the publish/save actions with no real DB or Next runtime; (3) prioritize the **security-critical invariants** — PUBLISHED-only filtering, no-PII `select` allow-lists, auth re-derivation (never trust client input), the website sanitizer, the slug-collision retry.
**Why:** The listing's risk is data exposure + a broken publish flow; pinning those invariants in fast, deterministic tests stops the silent regressions a one-time review can't keep catching. Vitest is the Vite/Next/TS standard — native ESM/TS, clean module mocking, fast (43 tests in ~150ms). The extraction also improves the code (pure helpers separated from server actions). Core logic modules sit at ~90–100% coverage; the low "all files" number is just the untested UI/RSC in the denominator.
**Alternatives considered:** Node's built-in `node:test` + tsx (zero deps) — rejected; mocking the Prisma/auth boundaries is awkward without `vi.mock`. Jest — heavier ESM/Next config. React Testing Library for components/RSCs — deferred (async Server Components don't render cleanly in RTL; lower ROI than the logic/security tests).
**Revisit when:** Client components worth testing appear (add RTL + jsdom), we wire real integration tests against a Neon **dev branch**, or CI should enforce coverage thresholds on `lib/**`.

## 2026-06-19 — Brand center: keep the progress score, DEMOTE the number; trust is review-solicitation-free
**Decision:** The `/practitioner/brand` center computes a 0–100 personal **progress** score per part (+ overall), but the **number is demoted in the UI** — off every at-a-glance face (tiles, chapter summaries, overall bar) and revealed only **on tap** inside a chapter. The moon fills to the score (a calm dial) and the named stage (Forming / On its way / Settled) carries the read; the moon `state` is *banded from* the score so they can never contradict. Brand law: the score is **personal progress, never a grade or a comparison to other practitioners.** Separately: `why_trusted` **never coaches soliciting client reviews** — it's read-only about reviews that exist, and the no-reviews path warns against requesting them.
**Why:** A 5-specialist research pass ([docs/audits/2026-06-19-brand-center-research.md](../docs/audits/2026-06-19-brand-center-research.md)) found that for this audience (solo MN practitioners — self-promotion-averse, perfectionism-prone, mostly not "thinking in brand"), a visible number reads as a *grade* and induces the exact anxiety the calm brand avoids; gamification research agrees progress numbers routinely backfire. The founder chose "soften, don't drop" — keep the concreteness (the moon dial + the named stage + the on-tap number + the guided "why it matters") without a graded face. The review rule is a hard compliance line: ACA/APA/AAMFT/NASW/NBCC prohibit therapists soliciting testimonials from current OR former clients, and the redesigned "Start here" can surface that step first — so coaching it would put a licensed counselor at risk. Guarded by a test (`tests/brand.test.ts` → "ETHICS: never coaches soliciting client reviews").
**Alternatives considered:** Show the raw number prominently (original draft) — rejected (graded/anxiety-inducing for this ICP). Drop the digits entirely (moons only) — rejected by the founder (loses the concreteness practitioners who don't grok "brand" asked for). Keep the worst-truthful state roll-up *and* a separate average score — rejected (they can contradict; state is now banded from the one score, and the worst-truthful helpers were removed as dead code). Keep the review-solicitation copy — rejected (ethics liability).
**Revisit when:** Real practitioners are observed using it (do the moons read as calm or still graded?), or the deferred items land — geo-targeting Serper, the guided first-run, the licensure/telehealth branch.
**Built by:** the research team + an adversarial honesty/correctness review; verified via screenshot (the real pages are Clerk-gated → a throwaway public preview route). Architecture: [docs/architecture/BRAND-CENTER.md](../docs/architecture/BRAND-CENTER.md).

## 2026-06-28 — Seeker side: a conversational onboarding agent + optional, anonymous-by-default accounts
**Decision:** The seeker experience (`/get-matched`) is a **real-time conversational agent** — voice by default (OpenAI Realtime + WebRTC), text-equal, plain form as the floor — that searches the directory and **surfaces practitioners as cards in a right-hand rail + a saved "basket"** mid-conversation. **Seekers are anonymous by default** (browse/match/basket all client-side, nothing stored server-side); an **account is the opt-in upgrade** (`/save-account` → `/dashboard`) that persists the saved list + sends one welcome email. Full rationale + the notable implementation calls: **ADR [0002](../docs/decisions/0002-seeker-onboarding-and-optional-accounts.md).**
**Why:** The product thesis is "not a directory — a decision tool"; a warm, adaptive conversation is better psychology (feeling heard, no blank-page anxiety) *and* a better matcher than a form, for people in a vulnerable moment. Anonymous-by-default is both the calmest psychology (no sign-up pressure; it's theirs) and the lightest compliance footprint — no sensitive "interested in these mental-health practitioners" record exists until the seeker explicitly opts in, keeping the whole loop outside the HIPAA question. Built compliance-ready now (minimal data, consent recorded for outreach); real-seeker launch still gated on Christie. Three implementation calls worth remembering: **model = OpenAI `gpt-4.1`/`gpt-realtime`** (the AI Gateway free tier 403s Claude); the **welcome email uses an atomic claim** (`UPDATE … WHERE welcomed_at IS NULL` before send, release-on-failure) so it sends exactly once and still retries a transient outage; and the **shared-column deploy-order rule** — `welcomed_at` is on `users` (read on every authed page), so the migration must be applied *before* the code or all authed pages 500 in the gap.
**Alternatives considered:** a long structured form as the primary path (rejected — worse psychology; kept as the `/get-matched/form` floor); inline practitioner cards in the chat stream (rejected — clutter; the rail+basket is calmer + persists); mandatory accounts (rejected — pressure + a sensitive record for everyone); deferring accounts until after the HIPAA call (rejected — built the minimal anonymous-by-default plumbing now, gated only the real-seeker launch).
**Revisit when:** Christie's HIPAA determination lands; a paid/direct Claude key makes the model worth revisiting; volume justifies a smarter matcher (ADR 0001's deferred structured fields); or accounts grow beyond "save a list."
**Built by:** lead build + an adversarial pre-deploy review (4 dimensions → per-finding verification; 10 confirmed findings fixed before ship); verified via `tsc` + ~397 tests + build + live smoke. Pairs with ADR [0001](../docs/decisions/0001-matching-workspace-curation-not-ranker.md) (the admin side of the same loop).
